# Taxonomy Proposal — Phase 2 (Hybrid) — **LOCKED v1.0.0**

Final taxonomy derived from empirical analysis of the 378 emails in
`emails_extracted_new.jsonl` and validated against the Pestana
reservations team's described workflow. Structure is **hybrid**: the
operationally grouped categories from the original Phase 1 handoff are
retained, but the Phase 1 intent layer is replaced by orthogonal
descriptive facets.

> **Status:** Locked v1.0.0 (2026-05-25). Phase 2 implementation
> consumes this version. Future changes go through `CHANGELOG.md`
> with a coordinated bump of the dependent JSON spec files.
>
> **Machine-readable companions:**
> `taxonomy.json` (vocabulary),
> `llm_output_schema.json` (LLM output contract),
> `agent_output_schema.json` (full pipeline output),
> `routing_rules.json` (deterministic routing table),
> `CHANGELOG.md` (version history).

---

## 1. Design principles

1. **LLM describes, router decides.** Classification + extraction is
   the LLM's job. Handling decisions and action selection are
   deterministic.
2. **Operational, not semantic.** Categories group emails by how the
   team handles them. Facets capture orthogonal observable properties.
3. **Forwarding-invariant.** The universal `Trade → Pestana RPA`
   wrapper is ignored; classification depends on the embedded
   original.
4. **Channel-agnostic.** Booking.com / Expedia / Mirai / etc. are
   metadata, not categories.
5. **MECE.** Every email fits exactly one category. A fallback
   category exists for genuinely unclassifiable emails.
6. **Evaluable.** Every category has ≥5 observed examples in the
   dataset. Every facet value is observable from the email content.
7. **No empty buckets.** Facets are orthogonal; a facet value that
   doesn't apply (e.g., a lifecycle stage on a system alert) simply
   takes `n/a` / `none` — no taxonomy bloat.

## 2. Categories (7 total)

### 2.1 `booking_notification`

**Operational definition.** A system-generated, templated email from a
booking channel or distribution system that informs the team about a
single booking lifecycle event. The team's standard workflow is to
audit the booking against the PMS and only reply if the audit
surfaces a mistake or follow-up question.

**Inclusion criteria.**
- New booking notifications from any channel (Booking.com, Expedia,
  Hotelbeds, Agoda, Synergy, Hopper, ODIGEO, EC Travel, BEMTours, Open
  Travel Service, BA Holidays, Schauinsland, Despegar, Juniper/Jet2,
  Dertour, etc.).
- Paid booking confirmations.
- Pre-arrival / check-in reminder notifications (Mirai, Despegar).
- Post-hoc modification notifications (e.g., Mirai "Modified
  Reservation").
- Post-hoc cancellation notifications generated by a channel.

**Exclusion criteria.**
- Channel-generated booking changes/cancellations are in §2.2 (the
  workflow there is different — review the change, not audit a new
  state).
  *Implementation note.* The line between "post-hoc notification of a
  modification" and "booking change to review" can be subtle. Default
  rule: if the email is a pure system templated notification with no
  human note, it's §2.1; if it requires the team to validate a change
  against contract/policy, it's §2.2. See borderline cases.
- Human-written booking-related requests are in §2.3.
- SiteMinder / PMS error emails are in §2.6.

**Distinguishing signals.**
1. Channel-templated subject line: `<Channel> Booking for #<ID>`,
   `Mirai: Checkin <Month> <DD>`, `Agoda Booking ID <ID> - CONFIRMED`,
   `Booking Confirmation | EDR-...`, etc.
2. Body has templated sections: `RESERVATION DETAILS`,
   `RESERVATION CONFIRMATION`, `PAYMENT DETAILS`,
   `Daily Room Rate Breakdown`.
3. No human greeting / signature in the inner email.

**Observed examples.** `email_72`, `email_127`, `email_133`, `email_319`,
`email_206`, `email_207`, `email_22`, `email_316`, `email_333`.

**Audit finding (output field).** Computed by the audit module:
`clean` / `missing_fields` / `suspected_error`. Drives whether the
human needs to act beyond routine audit.

**Estimated frequency.** ~270–290 emails (~74%).

### 2.2 `booking_change_or_cancellation`

**Operational definition.** An email about an existing booking that
requires the team to review or validate a change. Either system-sent
(channel cancellation/modification template) or human-written
(partner / guest requesting or negotiating a change).

**Inclusion criteria.**
- Channel-generated cancellation notifications (Booking.com, Expedia,
  Hotelbeds, Agoda, BA Holidays cancellation reports).
- Channel-generated modification notifications that require validation
  (not pure post-hoc passbooks — those are §2.1).
- Human-written modification requests for existing bookings.
- Human-written cancellation requests / cancellation-fee negotiations.
- Date / room / occupancy change requests for existing bookings.

**Exclusion criteria.**
- Brand-new booking requests (no prior booking) → §2.3.
- Stop-sales / inventory operational threads → §2.5.

**Distinguishing signals.**
1. Subject contains "Cancellation", "Modification", "Cancelamento",
   "Modified Reservation", "Change of booking".
2. Body references a specific existing booking reference + a change
   action.
3. Channel templates show "Cancelled On:" or "Modified On:" dates.
4. Human messages: greeting + reference to existing booking + change
   verb (`alterar`, `cancel`, `modify`, `change dates`).

**Observed examples.** `email_146`, `email_147` (Expedia
cancellations), `email_98` (front-office forward of change-of-booking),
`email_299`, `email_300` (Mirai modification), `email_361`
(cancellation negotiation).

**Estimated frequency.** ~50 emails (~13%).

### 2.3 `service_or_information_inquiry`

**Operational definition.** A human-written email (from a guest,
partner, agency, or internal Pestana staff) asking for information,
making a new booking request, or requesting a service that is not a
modification/cancellation of an existing booking.

**Inclusion criteria.**
- Policy / amenity / facility questions (RAG candidates).
- Availability or quote inquiries.
- New booking requests from partners, agencies, or direct guests.
- Internal Pestana staff booking accommodations for technicians,
  staff travel, project work.
- Operational requests that are not lifecycle changes (e.g., airport
  transfer requests, special arrangements).
- Withdrawals or acknowledgments of prior service inquiries.

**Exclusion criteria.**
- Inquiries specifically about payment / invoice / VAT / billing →
  §2.4.
- Modifications or cancellations of existing bookings → §2.2.
- Inventory / stop-sales operational threads → §2.5.

**Distinguishing signals.**
1. Human greeting + signature.
2. Free-form text in PT / EN / ES / DE.
3. Request verbs: `solicitamos`, `gostaria`, `please confirm`,
   `poderia`, `please book`.
4. Booking.com extranet relay format ("We received this message from"
   / "Recebemos esta mensagem de") — guest messages via OTA.
5. CRM case markers (`Case Number: 03XXXXXX [ ref:!00D0... :ref ]`)
   common.

**Observed examples.** `email_24` (guest parking question), `email_376`
(Vista Verde new booking), `email_337` (Soltrópico new booking),
`email_326`, `email_327` (Vostio internal technician booking),
`email_157`, `email_204` (withdrawals), `email_331`, `email_332`
(Booking.com extranet guest messages).

**Estimated frequency.** ~30–40 emails (~9%).

---

### 2.4 `payment_billing_or_rate_issue`

**Operational definition.** Email where the primary topic is payment,
billing, invoices, fiscal data, rates, tariffs, or commercial
contracts. Distinct from a booking lifecycle event; this is about the
*money* attached to it.

**Inclusion criteria.**
- Invoice requests, VAT / CIF / NIF / fiscal-data updates.
- Payment status questions, refund inquiries.
- Rate / tariff change requests under existing contracts.
- Commission disputes or partner billing questions.
- System-forwarded payment problem warnings (e.g., Mirai "Problems
  with your credit card").
- Internal finance team inquiries about a booking's financials.

**Exclusion criteria.**
- A booking notification that includes a VCC field but no payment
  question → §2.1.
- A cancellation negotiation that mentions fees but is primarily about
  the cancellation → §2.2.

**Distinguishing signals.**
1. Subject or body contains: `invoice`, `fatura`, `VAT`, `CIF`, `NIF`,
   `fiscal`, `factura`, `tarifa`, `rate`, `contract`, `pagamento`,
   `payment`, `refund`, `credit card`.
2. Money or finance is the dominant theme of the email body, not a
   side-mention.

**Observed examples.** `email_155` (Spanish CIF question), `email_99`
(Mirai credit card warning — system-forwarded but topically payment),
`email_329` (TAP contract rates), `email_330` (CIT Global tariff
change).

**Estimated frequency.** ~15 emails (~4%).

---

### 2.5 `inventory_availability_or_stop_sales`

**Operational definition.** Email about room inventory, allotment,
stop-sales, or operational availability coordination — typically a
partner reply or operational thread, occasionally a system-generated
availability alert.

**Inclusion criteria.**
- Partner replies to Pestana-initiated stop-sales requests.
- Allotment update or coordination threads.
- Stop-sales notifications generated by Pestana's stop-sales system.
- Mirai / channel availability alerts ("no availability for these
  dates").
- Inventory blocking / release / room closure operational discussions.

**Exclusion criteria.**
- Availability inquiries from a guest or partner that are part of a
  booking-request flow → §2.3.
- SiteMinder PMS delivery failures (system-level, not inventory) →
  §2.6.

**Distinguishing signals.**
1. Subject or body contains: `stop sales`, `stop-sale`, `allotment`,
   `availability`, `inventory`, `paragem de vendas`.
2. Typically threads with the partner's booked-allotment position.

**Observed examples.** `email_345` (CEDOK stop-sales reply),
`email_369` ([EXTERNAL] stop-sales thread), `email_205` (Mirai
no-availability alert).

**Estimated frequency.** ~10 emails (~3%).

---

### 2.6 `system_or_channel_delivery_exception`

**Operational definition.** A system-generated alert, error, or
exception notification from a channel manager, PMS, distribution
system, or OTA infrastructure that requires technical or operations
team attention.

**Inclusion criteria.**
- SiteMinder reservation delivery failure emails.
- Channel-manager-to-PMS delivery errors.
- "Reservation could not be found" / "duplicate or unmatched
  reservation" messages.
- Channel extranet alerts requiring login (e.g., easyJet holidays
  Extranet alert).

**Exclusion criteria.**
- Mirai credit card warnings → §2.4 (topic is payment).
- Availability alerts → §2.5 (topic is inventory).
- Stop-sales communications → §2.5.

**Distinguishing signals.**
1. Subject explicitly references a system or technical event:
   *"Siteminder reservation delivery failure"*, *"Booking Alert easyJet
   holidays Extranet"*.
2. Body contains: `unable to be delivered to your PMS`,
   `could not be found`.
3. Sender is a no-reply system address.

**Observed examples.** `email_346`, `email_347` (SiteMinder delivery
failures), `email_20` (easyJet extranet alert).

**Estimated frequency.** ~15 emails (~4%).

---

### 2.7 `other_or_unclear`

**Operational definition.** Fallback for emails that cannot be
confidently classified into one of the six operational categories.

**Inclusion criteria.**
- Auto-acknowledgments and contact-form confirmations with no
  operational content.
- Ambiguous emails where no category clearly dominates.
- Garbled, partial, or near-empty bodies after cleaning.
- Spam or off-topic.

**Distinguishing signals.**
- No clear inclusion match for §2.1 through §2.6.
- LLM confidence below the routing threshold (≤0.75).

**Estimated frequency.** ~5 emails (~1%).

## 3. LLM-predicted descriptive facets

Five orthogonal facets, each predicted independently by the LLM as a
separate JSON field.

### 3.1 `sender_type`

| Value | Meaning |
|---|---|
| `automated_system` | Email originates from a channel manager, OTA, distribution system, or other system (Booking.com, Expedia, Mirai, SiteMinder, etc.). |
| `partner_or_agency` | Human author at an external travel agency, wholesaler, DMC, tour operator, or contracted partner. |
| `direct_guest` | End-traveler / customer, either directly or via an OTA extranet relay. |
| `internal_pestana_staff` | Pestana property staff, internal department, or central reservations team member. |
| `unknown` | Cannot determine. |

**Boundary rule.** Classify by the *original author* of the embedded
content, not by the forwarder. A Pestana front-office forwarding a
partner email = `sender_type = partner_or_agency`. A property
forwarding a guest message = `sender_type = direct_guest`. An internal
operational email = `sender_type = internal_pestana_staff`.

---

### 3.2 `request_type`

| Value | Meaning |
|---|---|
| `policy_or_general_question` | Asking about a policy, amenity, service, or facility (potential RAG candidate). |
| `availability_or_quote_inquiry` | Asking if rooms/dates are available or for a price quote. |
| `new_booking_request` | Asking to create a booking. |
| `modification_request` | Asking to change an existing booking. |
| `cancellation_request` | Asking to cancel an existing booking. |
| `payment_or_billing_inquiry` | Asking about payment, invoices, VAT, refunds, billing. |
| `complaint_or_dispute` | Expressing dissatisfaction, asking for resolution. |
| `withdrawal_or_acknowledgment` | Retracting a previous request or acknowledging an answer. |
| `none` | No specific request — purely informational (most automated notifications). |
| `other_or_unclear` | Cannot determine. |

**Purpose.** Captures *what* the email is asking. Combined with the
category, this resolves the descriptiveness problem the Phase 1 intent
layer was trying to solve.

---

### 3.3 `booking_lifecycle_stage`

| Value | Meaning |
|---|---|
| `new` | Email concerns the creation of a new booking. |
| `paid` | Email concerns a booking already paid / prepaid. |
| `pre_arrival` | Email concerns an upcoming arrival / check-in. |
| `modified` | Email concerns a modification (made or requested). |
| `cancelled` | Email concerns a cancellation (made or requested). |
| `n/a` | No specific lifecycle stage (alert, exception, general inquiry). |

**Source.** Populated from
`extracted_fields.booking_identity.notification_type`. This is the
canonical field; the facet mirrors it.

---

### 3.4 `expects_human_response`

| Value | Meaning |
|---|---|
| `yes` | The email solicits a reply, decision, or follow-up based on its content and tone. |
| `no` | The email is purely informational. No reply solicited. |
| `unclear` | Cannot determine. |

**Framing note.** Routine audit-against-PMS that the team performs on
every channel notification is the *baseline floor* and is not counted
as a "response" here. The facet measures whether the email's own
content invites a reply.

---

### 3.5 `urgency_signal`

| Value | Meaning |
|---|---|
| `routine` | Normal handling. |
| `urgent` | Explicit urgency markers in subject or body (`URGENT`, `URGENTE`, `PLEASE REPLY`, payment-problem warnings, imminent-arrival timing). |
| `sensitive_complaint` | Complaint, dispute, dissatisfaction, sensitive issue. |

---

## 4. Router-computed handling flags

Decisions about handling. Derived deterministically from category +
facets + audit + retrieval. **Not predicted by the LLM.**

### 4.1 `outbound_action_required`

| Value | Derivation |
|---|---|
| `yes` | `expects_human_response = yes` OR `audit_finding ∈ {missing_fields, suspected_error}` OR `urgency_signal ∈ {urgent, sensitive_complaint}`. |
| `no` | `expects_human_response = no` AND (no audit_finding or `audit_finding = clean`) AND `urgency_signal = routine`. |
| `unclear` | `expects_human_response = unclear` and no overriding signal. |

### 4.2 `requires_internal_system`

| Value | Derivation |
|---|---|
| `yes` | Category ∈ {`booking_change_or_cancellation`, `payment_billing_or_rate_issue`, `inventory_availability_or_stop_sales`, `system_or_channel_delivery_exception`}, OR `audit_finding ≠ clean`, OR (`service_or_information_inquiry` AND `request_type ∉ {policy_or_general_question, withdrawal_or_acknowledgment}`). |
| `no` | Category = `booking_notification` AND `audit_finding = clean`, OR `request_type = policy_or_general_question` AND `kb_answerable = yes`. |

### 4.3 `kb_answerable`

Computed by **attempting** RAG retrieval, not predicted.

| Value | Derivation |
|---|---|
| `yes` | Retrieval returns at least one high-relevance chunk that directly answers the question. |
| `no` | Retrieval returns nothing relevant, or the question is booking-specific / operational. |

Only invoked when `category = service_or_information_inquiry` AND
`request_type = policy_or_general_question`. Otherwise skipped (default
`no`).

## 5. Routing rules (suggested first version)

```text
IF classifier_confidence < 0.75:
    action = manual_review_unclear

ELSE IF category = booking_notification:
    IF audit_finding = clean AND expects_human_response = no:
        action = audit_only
    ELSE:
        action = audit_with_attention
        // Surface missing fields, suspected errors, or embedded
        // remark for the human reviewer.

ELSE IF category = service_or_information_inquiry:
    IF request_type = policy_or_general_question AND kb_answerable = yes:
        action = draft_reply_with_rag
    ELSE IF request_type = withdrawal_or_acknowledgment:
        action = audit_only_with_note
    ELSE:
        action = escalate_to_reservations_team
        // Output template varies by request_type:
        //   new_booking_request    → escalate_new_booking_summary
        //   availability_inquiry   → escalate_availability_summary
        //   complaint_or_dispute   → escalate_priority (sensitive)

ELSE IF category = booking_change_or_cancellation:
    action = escalate_to_reservations_team
    // Output: change/cancellation summary with extracted fields.

ELSE IF category = payment_billing_or_rate_issue:
    action = escalate_to_payment_or_billing

ELSE IF category = inventory_availability_or_stop_sales:
    action = escalate_to_inventory_or_operations

ELSE IF category = system_or_channel_delivery_exception:
    action = escalate_to_technical_or_operations

ELSE:
    action = manual_review_unclear
```

Priority upgrades:
- `urgency_signal = urgent` → priority high
- `urgency_signal = sensitive_complaint` → priority high + sensitive flag

Each routed action carries a `routing_reason` string explaining
which facets and flags drove the decision.

**Canonical implementation.** `routing_rules.json` is the locked,
machine-readable version of these rules. The Router Agent walks them
in priority order; the first match wins.

## 6. Agent architecture — multi-agent system orchestrated with LangGraph

The system is implemented as a **multi-agent pipeline orchestrated by
LangGraph**. Each agent has a single, focused responsibility and emits
its output into a shared `AgentState` (a Pydantic object that grows as
the pipeline progresses). LangGraph defines the DAG, handles
conditional edges (notably the RAG branch), retries, and per-agent
traceability.

### 6.1 Agent flow

```
Preprocessor → Classifier+Extractor → Validator → Audit → Router
                                                            ↓
                                                (RAG if applicable)
                                                            ↓
                                                Output Generator → Guardrails → DB
                                                                                ↓
                                                                              API/Dashboard
```

### 6.2 Agents

| # | Agent | Role | Output block in `agent_output_schema.json` |
|---|---|---|---|
| 1 | **Preprocessor Agent** | Parse raw `.txt` thread → cleaned email schema. Deterministic. | `input_metadata` (snapshot) |
| 2 | **Classifier + Extractor Agent** | One LLM call: produce `classification` + `extraction`. | `llm_output` |
| 3 | **Validator Agent** *(novel multi-agent contribution)* | Second LLM call: critique the prior output, flag suspect fields, set `validation_result` and `revised_confidence`. | `validator` |
| 4 | **Audit Agent** | Deterministic field checks + lifecycle-conditional required-field logic + optional LLM anomaly flagging. | `audit` |
| 5 | **Router Agent** | Apply `routing_rules.json` in priority order. Deterministic. | `routing` |
| 6 | **RAG Agent** *(conditional)* — only when `category=service_or_information_inquiry` AND `request_type=policy_or_general_question` | Retrieve from ChromaDB; set `kb_answerable` based on retrieval relevance. | `retrieval` |
| 7 | **Output Generator Agent** | LLM call with route-specific template producing `audit_checklist` / `escalation_summary` / `clarification_draft` / `draft_reply` / `internal_notes`. | `output` |
| 8 | **Guardrails Agent** | Rule-based safety checks. Blocks unsafe drafts; forces escalation. | `guardrails` |

### 6.3 The Validator Agent — novel contribution

The Validator Agent is the *one place* in this architecture where the
multi-agent pattern produces value beyond what a single LLM call could
deliver. After the Classifier+Extractor produces `llm_output`, the
Validator runs a separate LLM call with:

- The original email content
- The proposed classification and extraction (as JSON)
- A critic-focused prompt: *"Read the email and the proposed
  classification + extraction. Identify any field where the proposed
  value contradicts the email content, is missing despite being
  clearly present, or appears hallucinated. Return a JSON with
  `validation_result` ('confirmed' or 'flagged'), `flagged_fields`
  (list of JSON paths), `reasoning_short` (one sentence), and
  `revised_confidence` (your floor estimate)."*

The Router uses `min(classification.confidence, validator.revised_confidence)`
as the effective confidence and triggers `manual_review_unclear`
when below the threshold. This catches LLM extraction errors before
any downstream decision uses them.

### 6.4 Tech stack per agent

| Agent | Tech |
|---|---|
| Preprocessor | Python stdlib (`email`, `re`, `mail-parser`) |
| Classifier + Extractor | Ollama + LiteLLM + Instructor (Pydantic JSON enforcement) |
| Validator | Same LLM client, different prompt |
| Audit | Plain Python (deterministic) + optional LLM for anomaly flags |
| Router | Plain Python evaluating `routing_rules.json` |
| RAG | ChromaDB + sentence-transformers (or Ollama embedding model) |
| Output Generator | Same LLM client, route-specific Jinja2 prompt templates |
| Guardrails | Plain Python (regex + rule list) |
| Orchestration | **LangGraph** with shared `AgentState` (Pydantic) |
| Persistence | SQLite + SQLModel |
| API | FastAPI + Uvicorn |
| Dashboard | Streamlit |

### 6.5 Why this matches the project's principles

- **LLM describes, code decides.** Only 3 of 8 agents are LLM-driven
  (Classifier+Extractor, Validator, Output Generator). The rest are
  deterministic. Routing is a JSON rule table, not a free-form LLM
  decision.
- **Traceable.** LangGraph records the `agent_path` per email; every
  decision can be reconstructed from the persisted `agent_output`.
- **Modular.** Each agent has a single contract (input block + output
  block in `agent_output_schema.json`). Replacing an agent does not
  ripple into others.
- **Defensible thesis framing.** "Multi-agent system orchestrated with
  LangGraph" with a "Validator Agent for output critique" is current
  research-aligned terminology that genuinely describes what the
  system does.

## 7. Validation status

### 7.1 Hotel-side validation

The Pestana reservations team confirmed the operational structure of
the proposed categories. Their answers to five operational questions
mapped 1:1 to the categories:

| Hotel's description | Category |
|---|---|
| "Automatic emails from partners (Booking.com, Agoda, ...)" | `booking_notification` |
| "Normal partner emails with agent requests" | `service_or_information_inquiry` (sender = partner) |
| "Forwarded customer requests from partner websites" | `service_or_information_inquiry` (sender = direct_guest) |
| "Emails from Pestana sites" | `service_or_information_inquiry` (sender = internal_pestana_staff) or property-forwarded guest messages |

The hotel also confirmed:

1. **The dominant workflow for booking notifications is audit, not
   reply.** *"We usually only answer if there's a mistake or follow-up
   question."* This motivates the `audit_finding` field.
2. **The biggest current inefficiency is auditing automated emails.**
   This is the dominant category (~74%) and where the agent adds most
   value.

### 7.2 Validation completed (partial) and deferred items

Partial manual validation was completed on a stratified subset of the
77-email labeling sheet. Ambiguous classifications surfaced during
validation were resolved in this proposal and propagated to the
machine-readable spec files. Full per-facet accuracy measurement is
deferred to **Phase 2 evaluation chapter**, using a ~30–50-email
manually labeled set against the live agent's predictions.

Items deferred to Phase 2 evaluation:

1. Per-category and per-facet classification accuracy.
2. Confusion matrix between predicted and human labels.
3. Tuning of the `kb_answerable` retrieval similarity threshold
   (currently 0.65).
4. Tuning of the low-confidence routing threshold (currently 0.75).
5. Validator Agent effectiveness — how often does it catch real
   classifier/extractor errors, and at what false-positive rate.

| Boundary rule "classify by inner content" | Forwarding wrappers are routing steps, not category signals. |
